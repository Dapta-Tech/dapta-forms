# Staff reach any workspace over MCP, the way they do in the web app

> Superseded for MCP sign-ins by [0003](0003-mcp-sign-in-maps-through-web-logins.md), then restored by [0004](0004-mcp-sign-in-link-first-directory-fallback.md): staff reach any workspace over an MCP sign-in again, judged on the directory's email or their linked members' email.

ADR 0001 said an MCP connection acts only in workspaces where the person has an active member, so the deployment's staff could not reach a customer's workspace over MCP although the web app's switcher lets them search and enter any workspace. We now give MCP connections the same staff rule: a person whose email, as the person directory holds it, is on one of the domains in `IAM_STAFF_DOMAINS` can search every workspace with `list_my_workspaces(search)` and act in any live one as an admin, through the same staff access grant (`member.access_grant = 'staff'`) the switcher mints. Because an MCP connection carries no session bearer to the identity service, the workspace is read from the identity service's database (read-only, the adapter that already maps a token to a person) instead of over its HTTP API. This supersedes 0001's consequence that a connection reaches only the person's own workspaces; everything else in 0001 holds.

## Consequences

- Staff is decided again on every request, never stored, on both doors: grant rows are never revoked, so a person who stops being staff (email moved off the domains, or a domain dropped from the list) loses every workspace they reached through a grant on the next request, even with the row in place. Over MCP the email is the person directory's, which keeps who a person is for up to a minute, so an email change in the identity service is seen within that. In the web app it is the email the session token carries: the auth provider says whether the person is staff on each request, and the header check, the home workspace, the workspace list and `enter` ignore grant rows unless it does.
- A grant never replaces a membership. A member row of the person that is not a grant (active, invited, or disabled by the workspace owner) is never converted: entering such a workspace through staff access answers `MEMBERSHIP_NOT_ACTIVE` and leaves the row as it was. A pending invitation by email is never adopted as a grant; it stays the member invite the team sent.
- The email comes from the identity service's user row, never from the request. It is as trustworthy as the identity service's guarantee that an address was verified and cannot be changed without verification. At the time of writing the token dForms receives carries no `email_verified` claim and dForms reads no verification column, so it cannot enforce "staff requires a verified email" itself; whoever runs the deployment confirms that guarantee before enabling `IAM_STAFF_DOMAINS` for MCP.
- Staff always pass `workspace_id`, even with one workspace of their own, and the agent is told everywhere (server instructions, `whoami`, `list_my_workspaces`, the guide) to confirm the workspace with the user before reading or writing, because a staff call can reach any customer's forms.
- A staff search never lists everything: it needs 3 letters or digits and returns at most 20, saying when more matched. The identity service's search has no index, and this keeps it cheap. Each result is named by the identity service's workspace id, which exists before dForms projects the workspace and stays the same after, so an agent never sees one workspace under two ids.
- Where the identity service names staff a member that dForms has not projected yet, staff act through a grant like anywhere else, and that row becomes the membership on the person's next projection. It used to answer `MEMBERSHIP_NOT_SYNCED`, which left an agent stuck on a workspace the search had just offered; a grant gives staff no more than they have in any workspace.
- A staff call outside the person's own workspaces is visible: its result says `access: 'staff'`, its audit line says `via: 'staff_grant'`, and the API logs a line per call.
- A key never becomes staff and never leaves its workspace. API keys work as in Dapta's own MCP, where staff may mint, list and revoke keys for any workspace and a key is a credential of the workspace, not of the person. Staff in a workspace through a grant (only while they are staff, judged on that request) create, list and revoke its keys like any admin. A key they create belongs to the grant row and acts as it (`admin`, in that workspace only); it keeps working until someone revokes it, whatever its creator's staff status later, because a key carries no person to judge staff by and revocation is the one clear way to end it. The workspace's owners and admins see such keys in their list marked as created by staff and can revoke them; offboarding someone from staff means revoking the keys they created, workspace by workspace, since nothing lists one person's keys across workspaces yet. Calls made with such a key are that key's calls (`via: 'api_key'`), not staff calls: they do not carry `access: 'staff'`, and the key's creation event is marked `staff_access` for product analytics. A grant that later becomes a real membership keeps its keys: from then on they are that member's keys, with the member's role, and follow the member out like any other. People who are not staff keep the uniform `NOT_FOUND` outside their workspaces.

  This replaces an earlier rule (PR #260) under which a grant never held a working key: creating one answered 403 `STAFF_ACCESS_NO_KEYS`, such keys answered 401 and were not listed, and a grant's keys were revoked when it became a membership. It left staff unable to set up an agent for a customer with a key, which Dapta's own MCP allows.

## Considered options

- Keep staff out of MCP (0001): staff then need a member in every customer workspace, or an API key from each customer, to help them from an agent.
- Forward to the identity service's HTTP API as the web app does: an MCP connection has no session bearer to forward, and minting one would mean dForms holding a credential it does not need.
- Reuse grant rows without re-checking staff: grant rows outlive the person's staff status, so access would never be cut.
- Never let a staff access grant hold a working API key (PR #260): no key outlives staff status, but staff cannot set up an agent with a key in a customer's workspace, unlike in Dapta's own MCP.
- Tie a grant's keys to their creator being staff now: a key carries no person, and the grant row's email goes stale when the person's email changes or they leave, so that check could not be made reliably.
