'@quill/api': patch

An MCP sign-in (`MCP_OAUTH_PROVIDER=workos`) now maps to its person through dForms' own database, the way the sibling calendars product does, and the API no longer reads the identity service's database.

- **The link.** Every verified web request records the WorkOS user id the session token carries (`workos_user_id`) on the member it acts as (`member.idp_subject`, written only when missing or different; the latest request takes it from any other member of the same account and logs `auth.idp_subject_recorded`), and stamps when the identity service vouched for that member (`member.login_seen_at`, the token's issue time, renewed about once a day, never backwards). A placeholder id the identity service writes on some migrated sessions is never recorded. Only a member bound to the same person the token names is linked: never a staff access grant row, a row bound to nobody, or someone else's row the web switcher reached by a shared email.
- **The sign-in.** A token's `sub` reaches the members carrying it and the same person's members in other workspaces, each only while its stamp is within `OAUTH_LINK_MAX_AGE_DAYS` (new, 30 by default, 1 to 365), and only active owners and admins. A sign-in that reaches none connects and acts nowhere, its tools saying to open dForms once (see the changeset on connecting before the link); a `sub` two different people carry gets a 403 that says to contact support. Each logs one line with its reason (`mcp.oauth_no_workspace` or `mcp.oauth_refused`), never the token or the subject. Each workspace counts once the person opens it in the web app within the window; existing members link that way with no new login. Invite adoption and projection never rebind a member another login bound in the meantime.
- **Removed.** The person directory and its settings (`IAM_DB_HOST`, `IAM_DB_PORT`, `IAM_DB_NAME`, `IAM_DB_SCHEMA`, `IAM_DB_USER`, `IAM_DB_PASS`, `IAM_DB_SSL_CA`): left set, they are ignored with one warning at boot, never a refused boot. `OAUTH_LINK_MAX_AGE_DAYS` is checked at boot whether or not MCP OAuth is on. With them goes staff access over an MCP sign-in (searching and entering any workspace): a sign-in acts in the person's own memberships only. Staff keep the web app's switcher, and API keys created there keep working over MCP. Matching a member by email at the MCP door is gone too.
- **Migration 0026** (both dialects, additive): the nullable `member.idp_subject` and `member.login_seen_at` columns, a unique index on (`idp_subject`, `account_id`), and an index on `member.external_id`. On Postgres it runs under `lock_timeout` and `statement_timeout`, so a busy table fails the boot fast instead of hanging.
- **Issuer fetches.** The AuthKit key set and authorization server metadata are now read with no redirect followed and a 64 KiB body cap, besides the time limit they already had.
