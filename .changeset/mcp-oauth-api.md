'@quill/api': patch
---

`/mcp` accepts MCP connections signed in through OAuth when `MCP_OAUTH_PROVIDER=workos`. With the provider unset, nothing changes.

- **Tokens.** The API verifies the AuthKit access token: RS256 against the issuer's published keys, `iss` and `aud` exact, `sub` and `exp` required, a `crit` header refused. The keys are fetched once on a cold start however many requests arrive, and again when a token names a key id the set lacks, at most once every 30 seconds, so a rotated key is picked up within that. While the keys cannot be read and none are cached, a signed-in request gets a 503 with `Retry-After`, not a 401.
- **Discovery.** `GET /.well-known/oauth-protected-resource/mcp` and `GET /.well-known/oauth-protected-resource` publish the protected-resource metadata, and `GET /.well-known/oauth-authorization-server` forwards AuthKit's authorization server metadata for older clients (503 while it cannot be read). All three answer 404 with the provider unset or the MCP endpoint disabled. The MCP host must route `/.well-known/*` to the API.
- **Who it acts as.** The token's subject is mapped to a person by reading the identity database (`IAM_DB_*`): the live user row with that provider id, and only if there is none, the live users its sessions link to it. More than one person, or an inactive or blocked one, is a 403 that says to contact support; nobody is a 403 that says to open dForms once. TLS is used unless the host is a loopback host, verified against `IAM_DB_SSL_CA` when it is set (the API logs once at boot when it is not); at most 4 connections and 5 seconds per query; nothing connects until the first sign-in, and the pool closes when the API shuts down. While the database cannot be read, a signed-in request gets a 503 with `Retry-After`, and API keys keep working. Each pod keeps who a subject is for a minute (nobody, or a refusal, for 10 seconds; an outage never), and a lookup it cannot answer first takes a token from a bucket keyed by the subject (429 past it).
- **Workspaces.** A connection reaches every workspace where the person has an active member, listed again on every request from dForms' own members: by the person's id, or by email only on a member nobody else holds yet. A staff access grant or a pending invitation never counts, and removing or disabling a member takes that workspace away on the next call. A person with no workspace yet connects, and the tools tell their agent to open dForms once.
- **Acting.** The tools hand the app's handlers an in-process principal (the member and workspace a call acts as) instead of an API key in a request header. A key's principal carries only its hash, and the key path still resolves it on every call (revoked key or inactive member: 401, the per-key limit, last use, `created_via = 'mcp'`). A connection's principal names a member with no key: re-read on every call (disabled or removed: 401 `MEMBER_NOT_ACTIVE`), with its live role and every rule an API key gets. Nothing that arrives over HTTP can carry a principal.
- **Limits and audit.** The MCP buckets count per member of the workspace each call acts in, and the audit line names member, person and workspace, never the token.
- **Boot.** A provider set without a person directory adapter, or with an `MCP_ALLOWED_HOSTS` that leaves out the host of `MCP_PUBLIC_URL`, refuses to boot. The API now closes cleanly on SIGTERM.
